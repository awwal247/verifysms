The example values are illustrative.

Documented Errors

Error| Meaning

"NO_NUMBERS"| No suitable numbers available
"NO_BALANCE"| Insufficient provider balance

Required Backend Behavior

1. Authenticate the user.
2. Validate the requested country and service.
3. Check permissions and applicable limits.
4. Request the number through the backend service.
5. Parse and validate the provider response.
6. Store the activation ID and associated metadata.
7. Return only information the authenticated user is authorized to access.

Do not mark an activation successful until the provider response has been validated.

9. CHANGE ACTIVATION STATUS

Purpose

Request a change to an activation's status.

Parameters

Parameter| Type| Required| Description
"action"| String| Yes| "setStatus"
"api_key"| String| Yes| Your API key
"id"| Number| Yes| Activation ID
"status"| Number| Yes| Requested status operation

Documented Status Parameters

Value| Documented purpose
"-1"| Cancel activation
"1"| Indicate that an SMS has been sent
"3"| Request another code
"6"| Complete or advance an activation, depending on its state
"8"| Indicate number use or cancellation, according to the documented operation

These values are provider-specific commands, not universal SMS verification standards. Follow the provider's status-transition rules.

Example Request

"GET /stubs/handler_api.php?action=setStatus&api_key=YOUR_API_KEY&id=ACTIVATION_ID&status=-1"

This requests cancellation. Do not send it unless cancellation is intended and permitted.

Documented Response Values

Response| Meaning
"ACCESS_READY"| Provider indicates the relevant operation is ready
"ACCESS_RETRY_GET"| Provider indicates a retry-related action is available
"ACCESS_ACTIVATION"| Provider indicates an activation-related result
"ACCESS_CANCEL"| Provider indicates cancellation
"EARLY_CANCEL_DENIED"| Early cancellation was denied

The documentation notes that early cancellation may be denied during the first two minutes.

Implementation Requirements

- Validate the requested transition before sending it.
- Check activation ownership.
- Prevent duplicate or conflicting status-change requests.
- Record the operation and result.
- Treat the provider response as authoritative for provider-side state.
- Handle denied and invalid transitions without silently changing local state.

12. ERROR-HANDLING STRATEGY

SMS-Man responses can include plain-text status strings as well as structured data.

The backend must not assume every successful HTTP response contains JSON.

Recommended Handling

Condition| Internal behavior
Invalid API key| Return a provider-configuration error and alert administrators
No numbers available| Return a clear availability error
Insufficient provider balance| Return a controlled provider-funding error
Unknown activation| Return a not-found response where appropriate
Invalid action| Treat as a provider integration error
Cancellation denied| Preserve the existing activation state
Network timeout| Return a temporary provider error
Invalid response format| Record a sanitized diagnostic and return a controlled error
Provider HTTP error| Inspect the response and classify it safely

Do not return raw provider exceptions, API keys, or internal stack traces to the frontend.

16. SECURITY REQUIREMENTS

1. Keep the SMS-Man API key in a server-side environment variable or secret manager.
2. Never send the API key to the frontend.
3. Require authentication for activation operations.
4. Verify ownership before allowing users to inspect or change an activation.
5. Restrict balance and provider administration operations to authorized staff.
6. Apply request rate limits and maximum active-activation limits.
7. Validate country, service, price, and status parameters.
8. Set connection and response timeouts.
9. Avoid logging API keys, full SMS contents, and unnecessary personal data.
10. Use HTTPS for all production communications.
11. Prevent users from guessing activation IDs to access another user's data.
12. Use idempotency or duplicate-request protection for activation creation.
13. Do not blindly retry number purchases after a timeout: the provider may have processed the first request even if the response was lost.
14. Reconcile uncertain operations with the provider before initiating another purchase.
15. Rotate any credential that has been exposed.

Use the provider only for authorized verification workflows. Do not use the integration to bypass another service's security controls or verification requirements.

17. RELIABILITY AND PERFORMANCE

Request Timeouts

Set explicit connection and read timeouts for outbound HTTP requests.

Polling

Use controlled polling intervals for activation status. Avoid excessively frequent requests.

Retries

Retry safe read operations selectively when transient network failures occur. Use backoff and a maximum retry count.

Do not automatically retry non-idempotent purchase operations without reconciliation.

Caching

Country and service lists can be cached. Price and inventory information should be refreshed often enough to avoid presenting stale availability as guaranteed.

Monitoring

Record:

- Provider request outcome
- Response latency
- Sanitized error category
- Activation state transitions
- Provider availability
- Failed and timed-out requests

Never log the provider API key.

20. FINAL IMPLEMENTATION DECISION

Integrate SMS-Man through a dedicated Django service layer.

The service layer should provide methods corresponding to the provider's documented operations:

- "get_balance()"
- "get_prices(country=None, service=None)"
- "get_number(country, service, max_price=None, currency=None, ref=None)"
- "get_status(activation_id)"
- "get_status_v2(activation_id)"
- "set_status(activation_id, status)"
- "get_countries()"
- "get_services()"

The Django REST Framework layer should authenticate users, enforce permissions, validate requests, manage activation records, and return normalized JSON.

The frontend must communicate only with the VerifySMS backend. The SMS-Man API key must remain private and server-side.
